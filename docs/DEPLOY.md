# Deploy: Vercel (frontend) + Render (backend) + Supabase (database + files)

The app runs the same way everywhere; only three environment variables decide "cloud mode":
`DATABASE_URL` (Postgres instead of SQLite), `STORAGE_BACKEND=supabase` (files in Supabase Storage
instead of the local disk) and `CORS_ORIGINS` (your Vercel URL).

## 1. Supabase (database + file storage)
1. Create a project (or reuse one). Region close to Render (Singapore).
2. Project Settings → Database → **Connection string → URI** (use the *session pooler* one, port 5432).
   This is `DATABASE_URL`. Tables are created automatically on first backend start
   (`database/schema.postgres.sql`); nothing to run by hand.
3. Project Settings → API → copy **Project URL** (`SUPABASE_URL`) and the **service_role** key
   (`SUPABASE_SERVICE_ROLE_KEY`). Never put the service key in the frontend.
4. Storage buckets `drawings`, `previews`, `exports` are created automatically (private).

## 2. Render (backend API, Docker)
1. New → **Blueprint** → pick the GitHub repo. Render reads `render.yaml` and builds `Dockerfile` (repo root)
   (LibreDWG is installed inside the image, so DWG conversion works in the cloud).
2. Fill the secret env vars when asked: `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
   `GEMINI_API_KEY`, `BOOTSTRAP_ADMIN_PASSWORD`. `JWT_SECRET` is generated by Render.
3. After the first deploy, open `https://<service>.onrender.com/healthz` → `"status":"ok"`.
4. Set `CORS_ORIGINS` to your Vercel URL (comma-separated if several), then redeploy.

Notes: the Starter plan keeps the service awake; the free plan sleeps and the first request takes ~1 min.
The container's disk is temporary — that is fine because files live in Supabase Storage and the
database in Supabase Postgres. Processing runs inside the API process (`WORKER_THREADS=1`).

## 3. Vercel (frontend)
1. New Project → import the GitHub repo → **Root Directory = `frontend`** (framework: Next.js).
2. Environment variable: `NEXT_PUBLIC_API_URL = https://<service>.onrender.com`.
3. Deploy. Sign in with `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD`, then change the password.

## 4. Local development stays the same
No `DATABASE_URL` → SQLite in `database/boq.db`; no `STORAGE_BACKEND` → files in `backend/data/`.
`tools/dev.sh` starts both servers. `tools/test_postgres.sh` runs the whole test suite on an embedded
PostgreSQL to prove the Supabase code path before deploying.

## Environment variables (backend)
| Variable | Local default | Cloud |
|---|---|---|
| DATABASE_URL | (empty → SQLite) | Supabase URI |
| STORAGE_BACKEND | local | supabase |
| SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY | — | from Supabase |
| GEMINI_API_KEY, GEMINI_MODEL_PRO, GEMINI_MODEL_FAST | your key, 2.5 pro / flash | same |
| JWT_SECRET | auto-generated file | Render generates |
| CORS_ORIGINS | http://localhost:3000 | https://<app>.vercel.app |
| BOOTSTRAP_ADMIN_EMAIL / _PASSWORD | from .env | set once, then change in app |
| DATA_DIR | backend/data | /data (temp disk) |
